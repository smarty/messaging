Doc error in this week's README, now fixed

The shape of what was found. The v4.0 and v4.1 work bounded the waits that caused the September incident. This sweep found the next ring of the same problem: places where a failure is swallowed, where a bound still does not exist, and where the recovery path is less faithful than the hot path. Three findings are shutdown or restart hazards that the v4.1.0 deferred handoff makes more likely, so they should ship in the same release. One is a years-old data-loss bug unrelated to stalls: message TTL is sent in the wrong unit.

Fixed · d1f5354 H1. Send on closed outbox channel at shutdown sqlmq/dispatch_processor.go:160 · dispatch_receiver.go:95 · deferred_handoffs.go:37

cleanup closes config.Channel as soon as Listen returns, which is milliseconds after Close. Handlers still inside Commit (up to the consumer's 5 s drain) and every deferred-handoff goroutine are sending on that channel. A send on a closed channel panics even inside a select; the ctx.Done() case cannot rescue it, and for streaming handlers that context is the hard context, which a graceful shutdown never cancels.

Two outcomes. A deferred goroutine panics in a bare goroutine and crashes the process mid-shutdown. A handler panics inside Commit after the SQL commit, transactional re-panics, retry re-runs the batch, and the side effects happen twice. That defeats the v4.1.0 guarantee that Commit returns success after the SQL commit. The README quick start calls consumer.Close() then dispatcher.Close() back to back, which is the triggering order.

Remedy Stop closing the channel. Nothing but the processor receives from it, so the close serves only one test assertion. Document that the consumer's Listen should return before dispatcher.Close().

Fixed · d4a1401 H2. TTL unit mismatch rabbitmq/writer.go:85-93

computeExpiration formats Dispatch.Expiration as whole seconds. The AMQP expiration property is a string the broker interprets as milliseconds, and the amqp091 source says so. A one-hour TTL goes on the wire as "3600" and the message is dropped after 3.6 seconds. Any value under one second becomes "1": one millisecond. Expired messages vanish with no error anywhere. The existing tests lock the wrong scale in. Present since the original writer commit.

Exposure depends on which services set Expiration. The one service inspected during this sweep does not, so this may be latent rather than active, but any consumer that is briefly behind a producer using TTLs is silently losing messages today.

Remedy Emit Milliseconds() with a floor of 1. Update the two tests. Call it out as a behavior change in the release notes, because a service that tuned its TTL against the wrong scale will see messages live 1000× longer.

Fixed · 89ce69b H3. An escaped panic hangs the worker silently streaming/worker.go:53-60

Listen defers waiter.Wait() and then runs deliverToHandler. A panic escaping Handle (a handler bug, a commit error without a retry wrapper, or retry.ErrMaxRetriesExceeded) unwinds into that deferred wait, which waits for the reader goroutine. The reader is parked in stream.Read on the hard context, which nothing cancels under the Drain or CurrentBatch strategies. The Go runtime prints a panic only after deferred calls return, so nothing is logged. Meanwhile the dead worker's reader keeps pulling deliveries from the shared stream into its own buffer, up to the prefetch window, starving the healthy workers.

The README written this week says the worker "crashes and the broker redelivers." That is true only for a stream that returns an error on read, which the test fake does and the real stream does not.

Remedy Give readFromStream a worker-local context derived from the hard context and cancel it in a defer registered after the wait, so it runs first. Recover in Listen to log an [ERROR] and fire a monitor callback before re-panicking, so the crash is attributable.

Fixed · bc3e221 H4. One subscription failing takes down its siblings streaming/subscriber.go:46 · connection_pool.go:43

The subscriber defers pool.Dispose(connection) on every exit path, including "queue does not exist" and a server-side consumer cancel. Dispose closes the AMQP connection unconditionally, which closes every channel on it. Every other subscriber's delivery channel closes, their workers exit, they dispose and reconnect after ReconnectDelay. A single 404 on one queue becomes a process-wide reconnect storm every 5 seconds (continuous with ReconnectDelay(0)), forever. Each cycle abandons every handled-but-unacknowledged batch on the healthy subscriptions, so the healthy queues see a steady stream of duplicates. The per-subscription log lines never say the cause was a sibling.

Remedy Dispose only on connection-level failures, or reference-count the pooled connection and close it only when the last user leaves and it is unhealthy. Have the rabbitmq connection expose closed state so Active can detect a dead cached connection instead of relying on this path.

Fixed · e876203 H5. Retry backoff overflows handlers/retry/handler.go:79-80

minBackoff << min(attempt, 63). Five seconds is about 232 nanoseconds, so the shift overflows int64 at attempt 31. Measured with Backoff(5s), MaxBackoff(5m): attempt 31 yields a negative delay, which WithTimeout treats as expired; attempts 62 and up yield zero. Combined with the effectively unlimited default MaxAttempts, a poison batch that has been retrying at the 5-minute cap for about two and a half hours flips into a hot loop that opens a database and AMQP transaction per iteration and logs a stack trace each time. Only triggers when MaxBackoff is set; with the default 0 the delay is constant.

Remedy Return maxBackoff once the exponent would exceed the available bits, and clamp any negative result to minBackoff.

Fixed · 89897e0 H6. Silent permanent stall in the dispatch processor sqlmq/dispatch_processor.go:128-130 · dispatch_store.go:112

writeBufferToSender returns false on a sender.Write error without logging it or reporting it to the monitor. The processor then retries the same buffer every RetryTimeout forever and never takes new work. A fully silent example: a dispatch with an empty Topic makes the rabbitmq writer return ErrEmptyDispatchTopic without logging. Because the startup read sets Topic = MessageType, the same row publishes fine after a restart, so the stall "fixes itself" on redeploy and is never diagnosed. Handlers keep acknowledging via deferral until the 8192 cap, then block with a message that blames the processor generically. Separately, Confirm discards RowsAffected, so a mismatch between rows updated and rows published is never seen.

Remedy Log the write error at WARN with the batch size. Compare RowsAffected to len(dispatches) in Confirm and log a mismatch. Add error callbacks to the sqlmq monitor in the next major version. Consider a poison-row policy: after N failures publish the batch one row at a time and park the failing row.

Fixed · 422cc74 H7. The status probe cannot see channel-level faults status/status.go:62-68, 86-101 · rabbitmq/adapter/amqp.go:87

basic.publish is asynchronous, with no confirms and mandatory=false. A 403 (no write permission on the exchange) or 404 (the configured Topic names a missing exchange) arrives as an asynchronous channel close that nothing observes. Probe N returns success and resets the window. Probe N+1's publish fails with a generic closed-channel error (504, tolerated) and the checker closes the connection. Probe N+2 reconnects and succeeds again. The window resets every other probe, so Status never reports the fault. The v4.0.0 notes promise that a denied permission bypasses the window; only connection-level 403 and 530 (bad credentials, no vhost access) actually do. The same mechanism means a successful probe proves only that frames reached the socket, not that the broker accepted or routed anything.

Remedy Register NotifyClose on the probe channel and surface the stored close reason on the next probe, or make the probe synchronous with publisher confirms bounded by the context. Either change also makes the probe mean something.

Fixed · e38436a H8. Deferred handoff uses the caller's context sqlmq/dispatch_receiver.go:66-70 · deferred_handoffs.go:27-43

TryDefer and the final blocking handoff run on the context passed to CommitWriter(ctx). For streaming handlers that is the hard context, near process lifetime, and the design works. For any request-scoped caller (an HTTP handler using r.Context(), a job with a timeout) the sequence is: Commit defers, returns nil, the handler returns, the context ends, the deferred goroutine exits, and the rows sit undispatched until some instance restarts. The only trace is an INFO line, or nothing at all on the deferred path. A long-running service may go weeks without a restart.

Remedy Hand the deferral and the final blocking handoff a lifetime context, config.Context or the processor's context, and keep the caller's context only for the initial bounded wait.

Fixed · 4ab7ec8 H9. The remaining unbounded waits in rabbitmq writer.go:37-58 · stream.go:72-77 · tls_dialer.go:45 · adapter/amqp.go:21 · stream.go:98 · reader.go:123

BrokerTimeout bounds TxCommit and TxRollback. Everything else that can park on the broker is still unbounded. Write discards its context and blocks in the kernel socket write once the send buffer fills; under a broker resource alarm a writer with a backlog stalls with no WARN cycle and no ErrCommitTimeout, because the stall never reaches the commit. Acknowledge checks the context once and then blocks the same way, ignoring the hard context. Connect honors the context for TCP only: the TLS handshake uses Handshake() not HandshakeContext, and amqp.Open sets no deadline, so a peer that accepts TCP and then hangs during auth wedges the status probe and every reconnect loop forever. Stream.Close (basic.cancel with noWait=false) and Reader.Close/Writer.Close (channel.close) are synchronous RPCs that callers run before the bounded connection close, so a graceful shutdown on a stuck channel hangs until SIGKILL.

Remedy Apply the same timer-plus-sever pattern to Publish and Ack, defaulting to BrokerTimeout. Set a socket deadline before the TLS handshake and amqp.Open, and use HandshakeContext. Use noWait=true for cancel, and skip or bound channel close when the connection is about to close anyway.

2. Medium: design and schema follow-ups

These are real, but most need a schema change, an interface change, or a design decision. Group them into a v4.2 or v5 plan rather than fixing piecemeal.

Medium M1. Outbox recovery rebuilds a different message than was committed sqlmq/dispatch_store.go:58-66, 79-89

The table stores only type and payload. Load reconstructs with Topic = MessageType, ContentType = "application/json", Durable = true, a fresh timestamp, and no partition, correlation ID, source ID, headers, expiration, or content encoding. In the common configuration, where TopicFromMessageType makes topic and type equal and the serializer is JSON, the recovered message matches. Anyone who sets an explicit topic, uses a non-JSON serializer, relies on partition keys for ordering, or traces by correlation ID gets a different message after a crash than on the hot path. Only the restart path exercises this, which is exactly when tracing matters most.

Remedy Persist the envelope: topic, partition, correlation and source IDs, content type and encoding, expiration, and headers as JSON. Treat it as a versioned migration.

Medium M2. Startup read has no ORDER BY and no LIMIT sqlmq/dispatch_store.go:72

After a multi-hour outage on a busy service, millions of mediumblob rows are loaded into one slice before the first send. The result is OOM, restart, OOM: a crash loop no instance can escape, because nothing is confirmed until the load finishes. The skipped test ReadFromLastSuccess shows paging was intended and never finished; the latestID plumbing already exists.

Remedy ORDER BY id LIMIT n and loop readPending until a short page.

Medium M3. MessageID arithmetic can be wrong and nothing detects it sqlmq/dispatch_store.go:43-50

MessageIDs are LastInsertId + i × stride. Contiguity holds for a multi-row simple insert under every InnoDB lock mode, so the hot path is sound when only this library writes the table. It breaks when auto_increment_increment differs from the configured stride (Group Replication multi-primary sets 7; Galera adjusts it per cluster size) and can break under interleaved bulk inserts by other writers. When wrong, Confirm marks other rows as dispatched: another instance's unpublished row can be confirmed and lost, and the real row is republished by every instance at every startup, forever. The AMQP message ID header is also wrong, which defeats consumer-side deduplication.

Remedy Check RowsAffected in Confirm (H6). Read @@auto_increment_increment at startup and warn when it differs from the stride. Or select the IDs back inside the transaction instead of computing them.

Medium M4. Cross-instance duplicates have no schema guard sqlmq/dispatch_store.go:72 · deferred_handoffs.go

Every instance's startup read publishes every other instance's pending rows, including rows another instance is holding in a deferred handoff. During a broker stall with a rolling deploy or liveness-driven restarts, duplicates scale with instances times restarts. Documented as at-least-once, but the incident scenario makes it N-fold rather than occasional.

Remedy An owner and claimed_at column pair, claimed on insert and reclaimed by the startup read only when stale. This is the schema change the v4.1.0 proposal deferred.

Medium M5. Undecodable message: block forever, or drop silently serialization/delivery_decoder.go:64-96 · connector.go:82-92 · streaming/worker.go:108-118

With the default Ignore*=false, one unknown type, unknown content type, or malformed body ends the stream read; the subscriber reconnects after 5 s; the broker redelivers the same message first; repeat forever. Everything behind it is head-of-line blocked, the stream-ended line is INFO, the decoder's WARN goes to a logger that defaults to no-op, and the status probe checks publishing only, so /status stays green. With Ignore*=true, the message is acknowledged with a nil Message and discarded; the worker never sees it. A consumer rolled out with a stale type registry loses every new event for hours with no error. Neither default is safe alone. The missing third outcome is "park with an alert."

Remedy A per-message poison policy: reject to a dead-letter queue (requires a reject method on Stream), or bounded redelivery then skip with an ERROR and a monitor count. At minimum raise the stream-ended line to WARN when the error is a serialization failure, and count skipped deliveries per batch in the streaming monitor.

Medium M6. Deliveries with a nil Message are acknowledged in silence streaming/worker.go:108-119

Four paths produce a nil Message: an empty payload, an Ignore* switch, a type filtered by AllowedTypes (swallowed to a successful read with no monitor signal), and a connector that is not wrapped in serialization at all. In the last case every message on the queue is acknowledged and discarded, the handler never runs, and the only symptom is BatchAcknowledged counts with no BatchHandled. It looks like a healthy, fast consumer.

Remedy Count skipped deliveries per batch and expose them: a WARN when a batch has acknowledgements but no handled messages, and a monitor callback in the next revision.

Medium M7. AllowedTypes cannot filter without also registering the type serialization/delivery_decoder.go:39-47

The ReadTypes lookup runs before the allow-list check, so a type you do not care about, which by definition is not in ReadTypes, hits the unknown-type path (M5) instead of being filtered. To use the option you must register every uninteresting type, which defeats it. A typo in the allow-list silently drops that type with no monitor signal.

Remedy Check AllowedTypes first; validate at New that every allowed name exists in ReadTypes; report filtered messages to the monitor.

Medium M8. No startup validation of the type registries serialization/config.go:9-16

Nil ReadTypes produces M5 on the first delivery of every queue. Two Go types mapped to one wire name in WriteTypes while ReadTypes maps it to one of them decodes half the messages into the wrong struct with zero-valued fields and no error. A service can publish a type it cannot consume. Nothing says so until production traffic arrives.

Remedy Fail fast in New on nil registries and many-to-one WriteTypes.

Fixed · 728c616 M9. Broker-initiated closes are never logged or reported rabbitmq/connection.go

The connection registers NotifyBlocked but never NotifyClose. ConnectionClosed fires only from an explicit Close. Heartbeat timeout, 320 CONNECTION_FORCED, the 30-minute consumer acknowledgement timeout (406), and a deleted queue all surface as a bare io.EOF from Stream.Read or ErrClosed from the next call. The reason is lost, and an open-minus-closed connection gauge drifts upward forever. Related: when a connection is severed while blocked, no ConnectionUnblocked ever arrives, so the blocked gauge the README tells services to page on sticks at 1 until a restart.

Remedy Register NotifyClose on connections and reader channels; log the *amqp.Error at WARN, fire ConnectionClosed, and return the stored error from Read instead of io.EOF. Emit ConnectionUnblocked when a blocked connection closes.

Fixed · 664b7dc M10. Every reconnect leaks a connection object rabbitmq/connector.go:60-63 · handlers/transactional/handler.go:23

defaultConnector.active appends every connection and nothing removes an entry when the caller closes it. Streaming retries every 5 s per subscription during an outage, batch and outbox writers reconnect per commit error, the status checker reconnects per failed probe, and transactional connects fresh per batch. Each leaks a closed connection with its buffers. Memory climbs slowly and only during the incidents when people are looking elsewhere.

Remedy Remove the entry in defaultConnection.Close, or drop the tracking entirely since callers already own their connections.

Fixed · 04c7d6b M11. One unsupported header value tears down the connection rabbitmq/writer.go:81

Dispatch.Headers passes straight through. amqp091 rejects uint, uint64, time.Duration, []string, and a nested map[string]any mid-frame, then shuts the whole connection down. The caller reconnects and retries the same message: a poison-message loop that churns connections (and leaks per M10). For an outbox it wedges publishing behind one row (H6).

Remedy Call amqp.Table(headers).Validate() before touching the wire and return a clear, non-retriable error.

Medium M12. Poison batch is a permanent head-of-line block with INFO-level evidence handlers/retry/config.go:64 · handler.go:53-58, 66

Default MaxAttempts is about four billion. Each failure logs at INFO. With one worker the whole queue stops. There is no dead-letter, no severity escalation, and HandleAttempted is the only signal. Also, ImmediateRetry matches by map key, so a wrapped error never matches and gets full backoff, and an uncomparable panic value (a struct with a slice) panics inside the recovery defer, landing in H3.

Remedy Escalate to WARN after a threshold. Add an on-exhausted hook for parking. Match ImmediateRetry with errors.Is and guard the map lookup with a comparability check.

Medium M13. Acknowledge-without-handle safety rests on the stream implementation handlers/retry/handler.go:25 · streaming/worker.go:136

When the context is cancelled, retry.Handle returns normally without invoking the inner handler. The worker then calls Acknowledge. Today the rabbitmq stream refuses on a done context, so the batch is redelivered. Any stream that acknowledges regardless of context (a future adapter, a wrapper passing Background) acknowledges an unhandled batch, which is message loss. retry logs nothing when it abandons a batch this way.

Remedy In deliverBatch, skip the acknowledgement when the hard context is done after Handle returns, and report it through BatchAcknowledged with the context error.

Medium M14. ReconnectDelay(0) and zero shutdown timeouts are honored literally streaming/manager.go:68-71 · subscription_config.go:71-90

A zero reconnect delay is a hot loop on any permanent error. A zero shutdown timeout on Drain or CurrentBatch fires ShutdownForced on every shutdown with a WARN that blames slow workers. Neither is defaulted the way the v4.1.0 options are. Separately, CurrentBatch always burns the full timeout under load, because the reader goroutine is blocked on the full buffer and only the forced path frees it (same root cause as H3).

Remedy Default non-positive values. Fix the reader cancellation with H3.

Medium M15. Outbox batch size is bounded only by channel capacity sqlmq/dispatch_processor.go:113-116

A service that raises ChannelBufferCapacity to 200 000 as a reaction to the stall incident will publish a 200 000-message AMQP transaction and issue a 4 MB UPDATE ... IN (...). Broker memory alarms and max_allowed_packet failures follow, and a failing Confirm then loops forever without draining.

Remedy A separate per-batch cap (default 1024) in fillEmptyBuffer, and chunked confirms.

Medium M16. Outbox receiver never rolls back on Close sqlmq/dispatch_receiver.go:46-57, 113-114

When Store or the SQL commit fails, the receiver returns the error without rolling back, and Close is a no-op. transactional covers this, but any direct user following the usual defer writer.Close() idiom leaks a pooled connection until its context ends, which for Background is forever.

Remedy Make Close call Rollback and ignore sql.ErrTxDone.

Medium M17. Status probe with no deadline can wedge every later /status call status/status.go:36-38, 86-101

The mutex is held across connect and write. If a caller passes context.Background(), a stalled write never fires ctx.Done(), the lock is held indefinitely, and every later call parks behind it. Whether the HTTP status wrapper supplies a deadline is not verified here. Also, a pre-cancelled context counts as a probe failure and severs a healthy connection.

Remedy Apply an internal default timeout when the context has none. Treat context.Canceled as "no result."

Medium M18. Non-zero Partition becomes the AMQP routing key rabbitmq/writer.go:48-49, 59-65

The field comment says "partition key for a hashing algorithm." On RabbitMQ it is the literal routing key. Fanout exchanges ignore it, so the common path is safe. On any direct or topic exchange declared elsewhere, a non-zero partition makes the message unroutable to every queue this library binds (with key "") and it is dropped silently because mandatory is false.

Remedy Document the mapping on the field, or set mandatory=true and log returns.

Medium M19. multi outside a transaction re-executes committed handlers handlers/multi/handler.go:15-19

retry.New(multi.New(a, b)) with each of a and b owning its own transaction: a commits, b panics, both run again. Correct only when multi sits inside the transaction wrapper. Not stated anywhere.

Remedy Document the composition rule.

3. Low: hygiene, docs, and footguns

  • Low rabbitmq/reader.go:54: the consume-failure log has one verb for two arguments, so the 404 for a missing queue prints as %!(EXTRA ...). Two lines in connection.go say "Unable able open."
  • Low rabbitmq/config.go:40: url.Parse error is discarded; an unescaped character in a password leaves Address nil and Connect panics on a nil dereference. tls_dialer.go:40-42 mutates the shared tls.Config.ServerName on every dial, a data race when several components connect at startup. An amqps:// URL with a nil TLS config sends plaintext to the TLS port while the log says "encrypted."
  • Low DispatchPublished and DeliveryAcknowledged(nil) count local buffer success, not broker acceptance. Under a blocked connection thousands are counted for frames the broker never read. Worth a note beside the README metrics table.
  • Low sqlmq: Confirm runs on the processor context, so a graceful shutdown between publish and confirm yields duplicates; run it on a short detached timeout. Startup read and live handoff can overlap within one instance if handlers commit before Listen runs; document "start Listen first."
  • Low handlers/sqltx never calls TransactionRolledBack though the monitor declares it. transactional rolls back after a failed commit, so every commit failure counts as two failures in monitors.
  • Low serialization: the encoder is a no-op when Payload is already set, so a retried slice with a mutated Message ships stale bytes. ContentEncoding is pass-through only and the decoder ignores it. The decorator's Writer() exposes Commit on a non-transactional channel via an unchecked type assertion. JSON numbers decode to float64 in any-typed targets, which loses precision on uint64 IDs.
  • Low StreamConfig.MaxMessageBytes promises truncation and is referenced nowhere. Delivery.Topic is the queue name, not the exchange, so a multi-topic consumer cannot tell sources apart.
  • Low streaming: FullThrottle allows a single Handle call, and one transaction, of up to 65 535 messages with no warning.
  • Low No vulnerability scanner runs in CI. Dependencies are current, but govulncheck is not installed locally and build.yml does not run it.

4. Corrections made during this sweep

Two documentation errors introduced this week were fixed in place, because they would have misled the migration work directly.

  • Fixed The README quick start and CLAUDE.md placed serialization under the outbox. That stores empty payloads, because the handler writes a bare Message to a receiver with no encoder. The correct layering, confirmed against a production service, is: outbox over the raw transport, then serialization applied separately to the transport for consuming and to the outbox connector for handlers. Both documents now say so, and the example compiles.
  • Noted The README claim that an escaped handler panic "crashes the worker and the broker redelivers" is wrong against the real stream (H3). It stays as written until H3 is fixed, and should be corrected in the same change.

5. Recommended sequencing

Shipped on this branch, for v4.1.0: H1 through H9 and M9, M10, M11, one commit each, all with tests and release notes. H2 (TTL units) is a behavior change and is called out as such.

A v5 or schema proposal: M1 through M4 (outbox envelope, paging, ID verification, ownership), M5 through M8 (poison-message policy and registry validation), plus the sqlmq error callbacks that H6 needs.

For the service migration checklist: pass a deadline-bearing context to Status (M17); never set ReconnectDelay(0) (M14); do not set Dispatch.Expiration until H2 ships; wrap serialization on the correct side of the outbox; call consumer.Close(), wait for its Listen to return, then dispatcher.Close().

6. What was checked and found sound

  • The v4.1.0 await/sever path: no way found for the sever itself to hang; a severed connection is never handed out again; concurrent and double Close are safe.
  • Heartbeat negotiation, blocked-notification relay goroutines (no leak, no blocking of the frame loop), closed-consumer detection, and multi-acknowledge tag ordering.
  • The streaming batching loop: the cached buffer length cannot strand a delivery; no strategy acknowledges before Handle returns; the pool mutex fix holds.
  • transactional and sqltx control flow, including the no-resources-before-defer property and the nil-context check.
  • The outbox sent flag, deferred-cap accounting, the ErrTxDone mapping, batch.Writer reconnect and close idempotency, Confirm's freedom from injection, and the (dispatched, id) index shape.
  • The status tolerance-window arithmetic and its reconnect hygiene, and connection-level 403/530 classification.
