Harden RabbitMQ Publishing Against Silent Stalls

Proposal — 2026-08-20 · Repository: github.com/smarty/messaging (v3) · Author: Claude, for Michael Whatcott · Status: draft, awaiting review

1. Background

The hobbes environment shows event-delivery delays of many hours. An investigation of billing-context, the harness/v2 pipeline, and this library found that a publisher can stall silently. The service stays healthy in every visible way while events sit undispatched. This library has three blind spots that make such a stall invisible:

  1. No client heartbeat. The adapter builds amqp.Config without a Heartbeat value (rabbitmq/adapter/amqp.go:14). The amqp091-go library then defers to the interval the broker offers. If a broker or a proxy offers zero, the connection runs with no heartbeats and no read deadline. A half-open TCP connection then blocks Publish and TxCommit forever.
  2. Blocked-connection notifications are discarded. When a RabbitMQ memory or disk alarm trips, the broker blocks all publishing connections: it accepts bytes and stops reading. TxCommit then blocks indefinitely with no error. The broker announces this state with a connection.blocked notification, but no code registers NotifyBlocked, so the announcement vanishes.
  3. The status checker swallows errors. status/status.go:29-40 returns healthy for every failure unless the error text contains the word "password". A service whose broker is unreachable still reports a green /status.
Evidence first. These fixes are visibility and detection hardening. They are worth doing on their own merits, but confirm the hobbes diagnosis (broker alarms, heartbeat configuration, stranded Messages rows) in parallel. None of these fixes unblocks a broker that is out of memory or disk.

2. Approach

All three fixes land in this repository (messaging/v3) as one minor release (target: v3.18.0). No fix changes the wire behavior of a healthy system. Consuming services adopt the release with a version bump; the new monitor callbacks are opt-in.

Decision (2026-08-27, during implementation): the release ships as v4.0.0, not v3.18.0. Rationale: safe adoption of the honest status checker requires deliberate caller-side work (failure-tolerance configuration and threshold verification), so the upgrade must not be reachable by an accidental go get -u; in Go, only a major version guarantees that. The scope also grows by one feature: status.Options.FailureThreshold(n) (Phase 3b below), so callers configure tolerance instead of each writing a decorator. The context-aware TxCommit redesign stays out (future v5).

Follow-up (2026-08-28): because v4 already breaks compilation, the optional blockedMonitor interface (T4) is dissolved: ConnectionBlocked(reason string) and ConnectionUnblocked() now belong to the monitor interface itself. Every monitor implementation adds the two methods (empty bodies suffice); the capability is fully discoverable and the type assertion is gone.

Fix 1 — Explicit client heartbeat

What changes

  • Add a Heartbeat time.Duration field to adapter.Config (rabbitmq/adapter/contracts.go).
  • Pass it through in amqpConnector.Connect: amqp.Config{..., Heartbeat: config.Heartbeat} (rabbitmq/adapter/amqp.go).
  • Add rabbitmq.Options.Heartbeat(value time.Duration) with a default of 10 seconds (rabbitmq/config.go), and populate the field in defaultConnector.configuration() (rabbitmq/connector.go).

Why 10 seconds

The amqp091-go library uses 10 seconds in its own Dial helpers, so the value is battle-tested. The client enforces a read deadline of three intervals, so a dead connection surfaces as an error within about 30 seconds.

AccomplishesA half-open TCP connection (idle-timeout LB, NAT, broker failover) now surfaces as an error within ~30 seconds. The retry loops in harness and sqlmq then reconnect and resume. Blind spot 1 closes fully.
Does not accomplishIt does not detect an alarm-blocked broker. A blocked broker keeps its socket alive and keeps sending heartbeats, so the connection looks healthy. Fix 2 covers that case.

Fix 2 — Register NotifyBlocked and surface the state

What changes

  • Extend the adapter.Connection interface with NotifyBlocked(chan amqp.Blocking) chan amqp.Blocking. The adapter package already exposes amqp.Delivery and amqp.Publishing, so this type stays consistent with the existing seam. The concrete amqpConnection delegates to the embedded *amqp.Connection.
  • In newConnection (rabbitmq/connection.go), register a channel and start one goroutine per connection that ranges over it:
    • On Blocking{Active: true}: log [WARN] AMQP connection blocked by broker (reason: %s); publishes will stall until the broker unblocks.
    • On Blocking{Active: false}: log [INFO] AMQP connection unblocked by broker; publishes resume.
    The amqp091-go library closes the channel when the connection closes, so the goroutine exits naturally. No new lifecycle management is needed.
  • Notify the monitor through an optional interface, checked once at connection construction: 
    type blockedMonitor interface {
    ConnectionBlocked(reason string)
    ConnectionUnblocked()
}
    Existing monitor implementations (for example rmqMonitor in billing-context) keep compiling unchanged. A service opts in by adding the two methods.

Note: amqp091-go already declares the connection.blocked client capability during the handshake (openTune), so the broker already sends these notifications today. This fix only stops discarding them.

AccomplishesAn alarm-blocked broker becomes visible the moment it blocks: a greppable [WARN] log line with the broker's stated reason, plus an optional monitor hook a service can wire to metrics and alerting (klaxon). The hobbes-style "hours of silence" becomes a one-line diagnosis. Blind spot 2 closes.
Does not accomplishIt does not unstick the publish. The broker still holds the connection until its alarm clears. Detection and paging are the goal; capacity on the broker is an operations concern.

Fix 3 — Honest status checker

What changes

  • In status/status.go, Status(ctx) returns the error from tryWrite unconditionally. Delete the strings.Contains(..., "password") filter.
  • Log each failure at [WARN] with the underlying error, so a failing health check explains itself.
  • Keep the existing reset behavior: on any write failure the checker closes and discards its cached connection, so the next probe dials fresh.

Behavior change, stated plainly

Today a service with an unreachable broker reports healthy. After this fix it reports failing, and the platform (load balancer, orchestrator) reacts according to its own policy. That reaction is the point: for a wedged publisher, a restart runs outbox recovery and drains the backlog. The httpstatus library already de-bounces through its own polling cadence; each consuming service should confirm its restart policy tolerates brief broker blips (see Trade-offs).

AccomplishesConnection failures, channel failures, and dial errors now fail /status. Operators see the failure where they already look. Blind spot 3 closes for every error the checker can observe.
Does not accomplishIt cannot detect an alarm-blocked broker. The checker's probe is a fire-and-forget Write on an async channel; a blocked broker accepts the bytes without error. Making the probe use publisher confirms would fix that but changes the probe's cost and semantics — recorded under Future Work, not in scope here.

3. Trade-offs and open questions

#ConcernAssessment
T1 Fix 3 changes default health semantics for every consumer of status. Intentional. The current behavior hides real outages. Risk: a transient broker blip marks a fleet unhealthy and the orchestrator restarts it. Mitigation: release notes call out the change; each service verifies its httpstatus thresholds before upgrading. Open question: do we want an Options.LenientErrors() escape hatch for one release? My recommendation: no — honest by default, no hatch.
T2 Default heartbeat value. 10s matches amqp091-go's own default and gives ~30s detection. A larger value (30s/60s) reduces already-negligible traffic but slows detection. Open question: also honor a heartbeat= query parameter on the broker URL? My recommendation: option-only for now; add URL parsing only if a real need appears.
T3 Extending the adapter.Connection interface breaks third-party adapter implementations. The interface is public but the only known implementation is the in-repo amqpConnection plus test fakes. A compile error with a one-method fix is acceptable for a minor release; the changelog documents it.
T4 Monitor extension style: optional interface vs. adding methods to monitor. The optional interface keeps every existing monitor compiling and makes adoption gradual. Cost: the capability is less discoverable. The changelog and the nop example mitigate this. Superseded 2026-08-28: with the v4 decision, the two methods moved into the monitor interface; see the decision callout in section 2.
T5 One goroutine per connection for blocked notifications. Negligible. Connections are few and long-lived, and the channel close bounds the goroutine's life to the connection's life.
T6 These fixes do not put a deadline on TxCommit itself. Correct. The heartbeat read-deadline covers the dead-socket case, and blocked-broker waits are intentional back-pressure. A context-aware commit is a larger v4-shaped change; see Future Work.

Phase 3b — Built-in failure tolerance (added 2026-08-27 with the v4 decision)

The checker reports a failure only after n consecutive probe failures; one success resets the count. Default: 5 (with the httpstatus default 1-second cadence, ~5 seconds of damping; services set their own cadence and threshold). Every tolerated failure still logs at [WARN].

5. Out of scope / future work

  • Context-aware commit. TxCommit has no deadline parameter. A cancelable commit is an API change fit for the v4 line, not this release.
  • Status probe with publisher confirms. Would let /status detect a blocked broker directly. Deliberately deferred; Fix 2 covers detection.
  • Legacy sqlmq gaps. The startup-only, unscoped, silent recovery sweep deserves its own proposal (periodic sweep, type scoping, a recovery count log line). Kept separate to keep this release small.
  • Harness recovery visibility in dashboards. RecoveryComplete is logged today; a metric would help. Belongs to the harness repository.

6. How we know it worked

  • Kill a broker connection at the TCP level (drop rule) — the publisher logs a write error and reconnects within ~30 seconds instead of hanging.
  • Trip a memory alarm in a test window — the service logs AMQP connection blocked by broker within seconds and the gauge rises.
  • Stop the broker — /status reports failing with the underlying error text.
  • All existing consumers compile and their suites pass after the version bump, with no code changes required beyond optional monitor adoption.
