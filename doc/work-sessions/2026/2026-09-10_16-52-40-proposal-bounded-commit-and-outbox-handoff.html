Bounded AMQP Commit and Outbox Handoff

Proposal · github.com/smarty/messaging/v4 · branch mikewhat/no-stalls · 2026-09-10
Target release: v4.1.0 (additive options, no interface changes) · Status: revision 2, for review
Revision 2 changes: the periodic recovery sweep is removed; a deferred handoff replaces it. The shutdown path is included in Fix 2. Defaults are accepted.

1. Background

On 2026-09-10 a consuming service stopped consuming from RabbitMQ. About 16 million messages accumulated. The process logged nothing. Its health check passed. A goroutine dump of a local reproduction showed the exact chain of blocked calls.

The chain, in order of cause:

  1. A queue bound to the subscription fanout exchange was down. The broker held the transaction commit that routed to it. defaultWriter.Commit waited without a deadline.
  2. The dispatch processor could not publish its first batch. It never drained the outbox channel.
  3. The startup loader read 12 580 undispatched rows from Messages. It filled the channel and blocked on the next send.
  4. Each handler committed its SQL transaction, then blocked on the same full channel inside dispatchReceiver.Commit. The handler never returned, so the worker never acknowledged its deliveries.

Three properties made this failure silent. No call had a deadline. No call logged while it waited. The status probe uses a plain publish, which a down queue does not stall. The v4.0.0 release added a heartbeat, blocked-connection notifications, and an honest probe. None of those fire for this case. The v4.0.0 proposal named the context-aware commit in its out-of-scope list. This proposal delivers it, and bounds the two waits that sit behind it.

One constraint shapes Fix 2. The handlers had already committed their SQL work when they blocked. On every restart, the broker redelivered the same batch and the service processed it again. A fix that returns an error after the SQL commit reproduces this problem on purpose, because the transactional handler panics on a commit error and the retry handler runs the batch again. After the SQL commit, dispatchReceiver.Commit must always return success.
One constraint shapes Fix 3. Many services use this module, and instances share an outbox table. Any recovery that scans the Messages table on a timer would republish rows that another process holds in flight, once per interval. So this proposal adds no periodic sweep. Recovery of rows that miss the handoff happens in memory inside the same process, and at the next startup as it does today.

Fix 1 — Bounded transaction commit and rollback (rabbitmq)

defaultWriter.Commit and defaultWriter.Rollback call TxCommit and TxRollback. Both are synchronous AMQP calls. The amqp091 client parks the caller until the broker answers, the channel errors, or the connection shuts down. The writer will run the call in a goroutine and wait with a timer.

On timeout, the writer must make the pending call return. Closing the channel does not work: Channel.Close is itself a synchronous call on the same stuck channel. Closing the connection does work. adapter.Connection.Close already uses CloseDeadline with a 5-second socket deadline, so the connection shuts down, every channel on it shuts down, and the pending call returns amqp.ErrClosed promptly. The status probe in v4.0.0 uses this same pattern. 

// rabbitmq/contracts.go
var ErrCommitTimeout = errors.New("the broker did not acknowledge the transaction within the commit timeout")

// rabbitmq/writer.go (sketch)
type defaultWriter struct {
	inner         adapter.Channel
	sever         func() error        // closes the parent connection; unblocks the pending call
	commitTimeout time.Duration
	// ... existing fields
}

func (this defaultWriter) Commit() error {
	err := this.await("commit", this.inner.TxCommit)
	if err == nil {
		this.monitor.TransactionCommitted(nil)
		return nil
	}
	this.logger.Printf("[WARN] Unable to commit channel transaction [%s].", err)
	this.monitor.TransactionCommitted(err)
	return this.tryPanic(err)
}

func (this defaultWriter) await(operation string, call func() error) error {
	completed := make(chan error, 1)
	go func() { completed <- call() }()

	timer := time.NewTimer(this.commitTimeout)
	defer timer.Stop()

	select {
	case err := <-completed:
		return err
	case <-timer.C:
		this.logger.Printf("[WARN] AMQP transaction %s did not complete within [%s]; severing the connection.", operation, this.commitTimeout)
		_ = this.sever()
		<-completed // bounded: the severed connection errors the pending call within the 5 s close deadline
		return ErrCommitTimeout
	}
}

defaultConnection.writer passes this.Close as the sever function. defaultConnection.Close uses sync.Once, so a later close by the owner is a no-op.

Downstream behavior, which needs no new code:

  • batch.Writer closes its handles on any error and reconnects on the next Write. The sqlmq dispatch processor sleeps for RetryTimeout (5 s) and tries the same buffer again.
  • The transactional handler panics on a commit error. The retry handler catches the panic and runs the batch again. This is the existing contract for a failed publish.
  • The TransactionCommitted(err) monitor callback fires with ErrCommitTimeout, so a service can count timeouts with errors.Is.

The option sanitizes its input the same way Options.Heartbeat does. A zero or negative value becomes the default. A caller cannot disable the bound by accident.

Fix 2 — Deferred outbox handoff (sqlmq)

dispatchReceiver.Commit stores the buffered messages, commits the SQL transaction, then sends each message into the outbox channel. Today that send waits on the channel or on ctx.Done(), and on cancellation it returns ctx.Err(). Both behaviors change.

After the SQL commit, Commit always returns nil

The rows are durable once the SQL transaction commits. From that point the handler's work is done and the caller must acknowledge. An error would cause a panic, a retry, and a second run of the handler's side effects. This applies to the new timeout path and to the existing shutdown path alike. On shutdown, the receiver logs an INFO line and returns nil. The startup read publishes the rows when the process returns.

On timeout, the handoff continues in the background

The send loop gains a timer of HandoffTimeout. When it fires, the receiver moves the messages it has not yet delivered to a deferred handoff: a goroutine that keeps sending them into the channel until it finishes or the context ends. The receiver logs a WARN with the counts and returns nil. The messages stay in memory, in the same process, so no table scan is needed and no other instance can see them. Ordering across batches is not guaranteed, which matches the outbox today, since concurrent handlers already interleave.

Deferred memory is capped

A stall that lasts for hours could accumulate deferred messages without bound. A shared deferredHandoffs tracker counts the messages held by deferred goroutines. When a new deferral would exceed DeferredHandoffCapacity (default 8192 messages, eight channels' worth), the receiver does not defer. It logs a WARN naming the cap and falls back to a blocking send, which is today's behavior plus the shutdown case. This is deliberate back-pressure: memory stays bounded, and the stall is already loud from Fix 1. 

// sqlmq/dispatch_receiver.go (sketch)
this.monitor.MessageStored(len(this.buffer))
remaining := this.handoff(this.buffer, this.handoffTimeout)   // sends until done, ctx ends, or timer fires
if len(remaining) == 0 {
	return nil
}
if this.ctx.Err() != nil {
	this.logger.Printf("[INFO] Context ended during handoff; [%d] committed message(s) remain in durable storage for the next startup.", len(remaining))
	return nil
}
if this.deferred.TryDefer(this.ctx, remaining) {
	this.logger.Printf("[WARN] Committed [%d] message(s) to durable storage, but the dispatch processor did not accept [%d] of them within [%s]. The handoff continues in the background.",
		len(this.buffer), len(remaining), this.handoffTimeout)
	return nil
}
this.logger.Printf("[WARN] Deferred handoff capacity [%d] reached; waiting for the dispatch processor to accept [%d] message(s).",
	this.deferred.capacity, len(remaining))
this.handoff(remaining, 0) // no timer: wait for the channel or for shutdown
return nil

// sqlmq/deferred_handoffs.go (sketch)
type deferredHandoffs struct {
	output   chan messaging.Dispatch
	capacity int64
	pending  atomic.Int64
}

func (this *deferredHandoffs) TryDefer(ctx context.Context, dispatches []messaging.Dispatch) bool {
	count := int64(len(dispatches))
	if this.pending.Add(count) > this.capacity {
		this.pending.Add(-count)
		return false
	}
	go func() {
		defer this.pending.Add(-count)
		for _, dispatch := range dispatches {
			select {
			case this.output <- dispatch:
			case <-ctx.Done():
				return // the rows are durable; the next startup publishes them
			}
		}
	}()
	return true
}

The tracker is created once in Options.apply, like the channel, and shared by every receiver built from that configuration. The context is the receiver's context, which the transactional handler derives from the worker's long-lived context, so deferred goroutines live until shutdown. A caller that cancels its context per request ends its deferred goroutines early. The rows are durable either way.

The default of 10 seconds is deliberately shorter than the 30-second commit timeout. A healthy handoff takes microseconds. A wait of several seconds already means the publisher is stalled. Ten seconds is long enough to ride out a normal broker failover, and short enough that handlers keep their consumer lag low.

Fix 3 — Shutdown-safe startup read (sqlmq)

dispatchProcessor.readPending runs once at startup and sends every undispatched row into the channel with a bare this.channel <- dispatch. If the channel is full when Close runs, that goroutine never exits, Listen never returns, and the host's shutdown hangs. The incident had exactly this state: goroutine 51 blocked on that send for 11 minutes. The send gains a ctx.Done() case. The startup read stays startup-only. The processor also logs how many rows the startup read found, which the v4.0.0 proposal asked for. 

// sqlmq/dispatch_processor.go (sketch)
func (this *dispatchProcessor) readPending() bool {
	dispatches, err := this.store.Load(this.ctx, this.latestID)
	if len(dispatches) > 0 {
		this.logger.Printf("[INFO] Startup recovery found [%d] undispatched message(s) in durable storage.", len(dispatches))
	}
	for _, dispatch := range dispatches {
		this.latestID = dispatch.MessageID
		select {
		case this.channel <- dispatch:
		case <-this.ctx.Done():
			return false
		}
	}
	if err != nil {
		this.logger.Printf("[WARN] Unable to load persisted messages from durable storage [%s].", err)
	}
	return err == nil
}

No monitor interface changes. Adding a method to rabbitmq.monitor or sqlmq.monitor breaks every implementer and forces a v5. The existing TransactionCommitted(err) callback carries ErrCommitTimeout. The handoff and recovery events are log-only in this release.

3. Trade-offs and open questions

1. Severing the connection affects every channel on it.
In this library, every CommitWriter lives on a connection that the caller opened for it: batch.Writer dials its own, and the transactional handler calls Connect per batch. Consumers use the streaming pool, which is separate. So a sever only hurts the writer that is already stuck. A caller who shares one connection between a consumer and a writer would lose the consumer stream on a commit timeout. The stream reconnects on its own. This is acceptable and will be documented.
2. No periodic sweep. Decided
Many services share outbox tables across instances. A timed sweep would republish rows another process holds in flight, once per interval. Revision 1 proposed such a sweep; it is withdrawn. Rows that miss the handoff are recovered in memory by the deferred handoff, and at the next startup by the existing read. The cost: a row that misses the handoff and outlives its deferred goroutine (a crash, or a caller whose context ends) waits for the next startup. That is today's behavior for every undispatched row.
3. The shutdown path returns success. Decided: included
dispatchReceiver.Commit returned ctx.Err() when the context ended during the handoff. The rows were committed, so the caller's panic caused a redelivery and a second run of the batch after the restart. It now returns nil with an INFO line. The existing test TestWhenTransactionContextCancelled_DoNotBlockWhenWritingToOutputChannel keeps its non-blocking assertion and changes its expected error to nil.
4. Handlers proceed while the broker is down, up to a cap.
With Fix 2, a broker outage no longer applies back-pressure to handlers until 8192 messages are deferred. Below the cap, handlers commit SQL, log a WARN, and acknowledge. This is the outbox pattern working as designed: the database is the source of truth and the broker is eventually consistent. Above the cap, handlers block as they do today, so memory stays bounded. A service that prefers immediate back-pressure can set DeferredHandoffCapacity to 1. A service that wants a larger buffer raises it.
5. Deferred messages are lost from memory on a crash.
They are not lost from the database. The startup read publishes them. This is the same guarantee the outbox gives every message today between SQL commit and broker confirm.
6. Write can still block on the socket.
A broker under a resource alarm stops reading the socket. Publish then blocks in a kernel write, before any transaction commit. Fix 1 does not bound that. The v4.0.0 blocked-connection notification and the honest status probe cover that case, and a restart clears it. Bounding Write would need a socket write deadline in the adapter, which is a separate change.
7. Time-based tests.
The new behaviors are timer driven. Tests will use timeouts of a few milliseconds against fakes that block until released, so each test proves the timer path without sleeping for long. The suite runs with -timeout=1s, so every test must complete well under that.
8. Default values. Decided: accepted
30 s commit, 10 s handoff, 8192 deferred messages. A healthy commit takes milliseconds, so 30 s is generous and only matters when something is wrong. Together with the 5 s close deadline and the 5 s retry sleep, a stuck publisher produces one WARN cycle about every 40 s.

5. Out of scope / future work

  • Bounded Publish. A socket write deadline in the adapter, for brokers that stop reading under a resource alarm. Covered today by the v4.0.0 status probe and a restart.
  • Status probe with a transactional publish. Would let /status detect a down queue on the probe topic. Deferred in v4.0.0 and still deferred. Fix 1 makes the stall loud and self-recovering, which reduces the need.
  • Monitor callbacks for handoff timeouts and deferred counts. Needs a monitor interface change, so it belongs to a v5 or to an optional interface checked by type assertion.
  • Periodic outbox recovery. Withdrawn from this proposal because instances share tables. A safe version needs ownership (a per-instance column or lease) in the Messages schema, which is a schema change for every service.
  • Consumer-side adoption. The consuming service's upgrade to v4 happens in a later session and is not part of this work.

6. How we know it worked

Reproduce the incident against a test broker with one queue bound to the target exchange and stopped.

  • Within 30 s: one WARN AMQP transaction commit did not complete, one WARN Unable to commit channel transaction, and a reconnect. The pattern repeats about every 40 s.
  • Within 10 s of each handler batch: one WARN Committed [N] message(s) ... The handoff continues in the background. The consumer's acknowledged count keeps climbing. The queue does not back up.
  • After about 8192 deferred messages: the capacity WARN appears and handlers block. Consumer lag grows, memory does not.
  • Start the queue. Within about 40 s the publish and confirm counters climb, deferred goroutines finish, and handlers resume. No restart.
  • Stop the process while the channel is full. Listen returns within the host's shutdown timeout. Handlers that were mid-handoff log the INFO line and acknowledge. The next start logs Startup recovery found [N] and publishes them.
  • Compare with the 2026-09-10 goroutine dump: no goroutine sits in Channel.call, readPending, or dispatchReceiver.Commit for longer than the configured bounds, except a receiver that is intentionally blocked at the deferred cap.
