Findings, most severe first

1 rabbitmq/connection.go:29 correctness confirmed quick fix

A blocking monitor callback can wedge the whole connection

A slow or blocking monitor.ConnectionBlocked/ConnectionUnblocked callback can wedge the entire AMQP connection: amqp091-go's dispatch0 delivers Blocking notifications with an unconditional blocking send from the connection's frame-demux goroutine, and watchBlockedState drains the capacity-1 channel synchronously through user callback code.

Failure scenario A broker memory alarm flaps blocked/unblocked/blocked while a service's ConnectionBlocked callback blocks (a synchronous alert call that hangs during the very incident it reports). Notification 1 is in the callback, notification 2 fills the capacity-1 buffer, notification 3 blocks dispatch0 (amqp091-go v1.10.0 connection.go:664-670, a blocking send with no select) — the reader goroutine stops processing frames, so deliveries, RPC replies, and Close all stall. The stall-prevention feature itself creates a silent stall.

FixDrain with select/coalescing, or invoke the monitor callbacks off the drain path.

2 status/config.go:53 correctness confirmed decision

The default damping window is ~5 seconds, not ~30

The default FailureThreshold of 5 counts probes, not time. With httpstatus's default 1-second cadence (that library has no tolerance of its own), the out-of-the-box damping window is only about 5 seconds — far below the release notes' own guidance that the window must exceed a rolling broker restart or failover election (~30s+).

Failure scenario A service upgrades to v4 leaving both defaults in place. A routine 30-second broker rolling restart produces ~30 consecutive probe failures; /status goes red after ~5 seconds and the orchestrator restarts the fleet mid-maintenance — exactly the hasty restart the threshold exists to prevent.

DecideRaise the default, or switch to a time-based tolerance (tolerate failures for a configured duration since the first failure), which is self-contained and immune to cadence changes made in a different library.

3 status/status.go:40 correctness confirmed decision

Credential errors lost their fail-fast path

v3 returned any error containing password on the first probe; v4 routes ACCESS_REFUSED/auth errors through the same tolerance counter as transient blips. Neither the code nor the release notes re-establish immediate reporting for definitive failures.

Failure scenario A pod deploys with a rotated or wrong RabbitMQ password. Under v3 the first /status probe failed and the rollout halted at the first pod; under v4 with the default threshold of 5, every new pod reports healthy for 4 probes — long enough for a readiness gate to pass and the rollout to replace all healthy old pods before the fleet-wide auth failure surfaces. TestWhenWriteFailsWithPasswordError_ReturnUnderlyingError passes only because Setup pins FailureThreshold(1), masking the regression at the default.

DecideShould definitive auth errors bypass the tolerance counter? That would partially restore the v3 fail-fast intent.

4 status/status.go:63 correctness confirmed quick fix pre-existing lines

The probe leaks a live connection when Writer fails

tryConnect leaks a live AMQP connection on every probe where Connect succeeds but connection.Writer fails: this.connection stays set with this.writer nil, tryWrite returns without Close (Close runs only on Write failure), and the next probe re-dials and overwrites this.connection without closing the old one.

Failure scenario A broker that accepts the AMQP handshake but fails channel.open leaks one TCP connection per probe — ~720/hour at a 5s cadence — each pinned forever in defaultConnector.active (rabbitmq/connector.go:62, never pruned on individual Close) and each now carrying a parked watchBlockedState goroutine. The lines are pre-existing, but the honest checker makes sustained failing-probe loops a first-class expected state, and this branch attaches a goroutine to every leak.

FixClose and nil the connection in the Writer-failure branch.

5 rabbitmq/connection.go:24 correctness confirmed quick fix

The watcher goroutine has no exit of its own

watchBlockedState exits only when the notification channel closes, and defaultConnection.Close gives it no exit signal — yet the release notes tell adapter.Connection implementers that return receiver is a sufficient fake, which never closes the channel.

Failure scenario A service that wraps adapter.Connection via the public rabbitmq.Options.Connector seam using the documented one-liner leaks one permanently parked goroutine (plus the captured connection object) per Connect/Close cycle; under connection churn this grows without bound and trips goleak-style detectors in downstream suites. The in-repo test fixtures already leak one watcher per test the same way.

FixSelect on a done channel closed by Close(), bounding the watcher's life regardless of the inner implementation.

6 status/status.go:53 correctness confirmed decision

The probe can block forever while holding the checker mutex

The status probe write can block indefinitely while holding the checker mutex during a prolonged broker alarm, contradicting the release notes' claim that "a blocked broker does not fail /status": defaultWriter.Write ignores its ctx and uses a deadline-free AMQP Publish, and a blocked broker stops reading the socket.

Failure scenario During a prolonged memory/disk alarm the probe connection's TCP send buffer eventually fills; one Status call wedges inside Write while holding the lock, every subsequent /status request queues on the mutex and times out at the HTTP layer — which most platforms count as a failed check — triggering the restart loop the notes say is the wrong reaction, with no error ever logged by the failure-threshold path.

DecideAdd a write deadline to the probe path, or amend the release-notes claim to describe this behavior honestly.

7 status/config.go:38 docs confirmed quick fix

FailureThreshold documentation is off by one probe

The godoc says the option "sets how many consecutive probe failures Status tolerates (returning nil) before it reports the error", but the code reports on the Nth failure, tolerating only N−1. The tolerated-failure log line (%d of %d tolerated) repeats the overstatement.

Failure scenario An operator sizes a damping window per the doc, sets FailureThreshold(6) expecting 6 tolerated failures (~35s at a 5s cadence), but /status actually fails on the 6th probe (~30s) — one probe interval before the window they validated against their longest routine broker event. The godoc's own third sentence and the test name TestFailureThreshold_DefaultToleratesFourConsecutiveFailures confirm the code intent.

FixCorrect the godoc's first sentence and the log wording.

8 doc/release-notes-v4.0.0.md:55 docs confirmed quick fix

"About 30 seconds" is really about 15

The claim that a dead socket "surfaces as an error within about 30 seconds" is wrong by 2x: amqp091-go v1.10.0 starts the heartbeater at interval Heartbeat/2 (connection.go:1047) and sets the read deadline to 3× that interval (connection.go:815), so a 10s heartbeat yields a ~15-second read deadline.

Failure scenario Operators size restart thresholds and damping windows against these numbers and assume ~30s of network-stall tolerance; any read stall over ~15s already tears down the connection, causing unexpected connection churn during network pauses the fleet was sized to survive. The proposal HTML repeats the same ~30s figure.

FixCorrect the release notes and the proposal to ~15 seconds, or double the default heartbeat if ~30s was the intended budget.

9 rabbitmq/config.go:73 correctness confirmed quick fix

Options.Heartbeat accepts self-defeating values

A negative duration survives amqp091-go's pick() as the negotiated value, which disables the client heartbeater and read deadline (heartbeater guard interval > 0) while sending uint16(-1) = 65535 seconds to the broker; a sub-second positive value truncates to 0 and silently defers to the broker, colliding with the documented Heartbeat(0) escape-hatch semantics.

Failure scenario A caller computes the heartbeat from config (a misparsed env var, value-minus-margin arithmetic) and passes −1s or 900ms. Every test passes (fakes just record the duration), the fleet runs with no client heartbeat and a 65535-second broker-side timeout, and the dead-socket blind spot this v4 release exists to close is silently reopened.

FixValidate or clamp, as the sibling option status.Options.FailureThreshold already does with max(value, 1).

10 rabbitmq/connection.go:24 correctness plausible optional

A blocked frame can be dropped during registration

NotifyBlocked is registered after amqp.Open returns, but the connection's dispatch goroutine starts before the handshake completes, and dispatch0 silently drops connection.blocked frames that arrive while the listener list is empty — so a blocked notification landing in the registration window is lost with no log and no monitor callback.

Failure scenario Narrow but real: an alarm-related blocked frame delivered between handshake completion and the NotifyBlocked call is dropped, and the service believes the connection is unblocked until the next block/unblock transition, which may be hours away. Stock RabbitMQ usually sends connection.blocked lazily on first publish (after registration), which shrinks — but does not eliminate — the window.

FixRegister the channel before or during adapter Connect; requires a small reshape of the adapter seam.
