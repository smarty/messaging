2Where connections live in a -context service

A service composed the way the README shows holds three AMQP connections, each owned by a different caller and each failing independently. Handlers never touch AMQP at all: they write rows, and the dispatcher publishes them.

3Connecting

Connect is three network round trips (TCP, optional TLS, AMQP handshake) followed by local setup. All three trips run under one deadline. Without it, a peer that accepts TCP and then goes silent would park every reconnect loop and the status probe forever.

4Inside a connection: goroutines, channels, lifecycle

Every connection starts three goroutines. Two of them exist to move broker notifications from amqp091's frame-reader goroutine to your logger and monitor without ever letting that frame reader block. The third turns a close the broker or network initiated into the same observable event as a close you asked for.

5awaitBroker: the one bounded-wait pattern

Six different channel calls (publish, commit, rollback, acknowledge, channel close, consumer cancel) can park with no deadline of their own. Some are synchronous RPCs waiting for a reply frame; some are plain socket writes to a broker that has stopped reading. All of them go through one function.

What is not under awaitBroker. The calls that set a channel up run as plain synchronous RPCs: channel.open, tx.select, queue.declare, exchange.declare, queue.bind, basic.qos, and basic.consume. They run on a connection that just completed its handshake, and the heartbeat fails a dead socket within about 15 s, but a broker that is alive and simply not answering RPCs would park them. Treat this as a documented gap, not a guarantee.

6Publishing through batch.Writer

The outbox dispatcher never calls rabbitmq directly. It hands a buffer of dispatches to batch.Writer, which turns each buffer into one AMQP transaction. The sequence below is one successful Write; the list after it is what happens on any error.

When any step fails

  1. rabbitmq writerReturns the error. On a timeout that error is a sentinel and the connection is already severed. On a 404 at Commit with PanicOnTopologyError on (the default) it panics instead; the status probe recovers that panic, the outbox does not.
  2. batch.WriterReturns zero written and calls closeHandles: writer.Close (bounded channel close, a no-op on a dead connection), then connection.Close, then forgets both. The next Write redials.
  3. sqlmq processorLogs [WARN] Unable to publish [n] message(s) to the transport […]; retrying in [RetryTimeout], sleeps, and retries the same buffer. Rows stay undispatched until Confirm succeeds.
  4. on retryA fresh connection and channel, the same dispatches. If the broker had in fact committed before the sever, the messages are published twice. Consumers already tolerate redelivery for other reasons.

The status probe is the same shape. status.Checker keeps its own connection and CommitWriter, publishes one empty dispatch, and commits. A 403, 404, or 530 at commit is definitive and bypasses the tolerance window. If the caller's context ends first, the probe closes its connection and waits at most SeverTimeout (5 s) for the parked call to return.

8Four scenarios, end to end

A. The commit stall

A queue bound to the exchange is unavailable, so the broker holds the tx.commit reply. With no bound, the writer would wait forever, the outbox channel would fill, every handler would park on the handoff, and nothing would acknowledge.

B. The broker closes the connection (node restart, missed heartbeats)

  1. amqp091Receives connection.close, or misses three heartbeats (15 s), or reads EOF. It shuts the connection down: every channel's error stream fails, the deliveries channels close, and the close notification gets the reason.
  2. watchCloseRuns closer.Do: closes done, logs [WARN] AMQP connection closed by the broker or network [reason], fires ConnectionClosed, releases the connection from the connector. relayBlockedState exits on done; if the connection was blocked, ConnectionUnblocked fires.
  3. stream.ReadSees deliveries closed and runs endReason. amqp091 fans the connection error out to every channel, so the channel close notification usually carries the same reason and Read returns it; if nothing arrives within 50 ms it returns io.EOF.
  4. workerLogs [INFO] Stream […] ended [EOF], closes its buffer, finishes the current batch if one is in flight, and exits. Its acknowledgement fails fast because the channel is gone; the broker will redeliver.
  5. subscriberSees workersDone, closes the stream (bounded cancel, returns immediately on a dead connection), closes the reader (bounded channel close, same), and disposes the pooled connection because Closed() is true.
  6. managerLogs [INFO] Subscription to stream […] concluded; reconnecting in [reconnectDelay], sleeps, and calls pool.Active, which dials a new connection (section 3). Sibling subscriptions on the same connection do the same thing in parallel; the first one to reconnect creates the connection the others reuse.

C. A resource alarm blocks the connection

  1. brokerRaises a memory or disk alarm. It sends connection.blocked to every connection and stops reading from connections that publish. Consumers keep being served.
  2. watchBlockedStateLogs [WARN] AMQP connection blocked by broker (reason: …); publishes will stall until the broker unblocks. and fires ConnectionBlocked(reason). Wire this to a page: a restart does not help.
  3. writer.WriteThe next basic.publish fills the socket buffer and parks in the write. awaitBroker("publish") waits 30 s.
  4. awaitBrokerSevers the connection, returns ErrPublishTimeout with zero written. watchBlockedState's input closes while blocked, so ConnectionUnblocked fires and the gauge returns to 0 for that connection.
  5. sqlmq processorRetries after RetryTimeout on a new connection, which is blocked again on its first publish. This repeats, one warning per cycle, until the alarm clears. Rows stay undispatched and durable. Handlers keep committing; after HandoffTimeout their dispatches go to the deferred handoff goroutine, up to DeferredHandoffCapacity, after which handlers block.
  6. brokerClears the alarm and sends connection.unblocked to connections still open. The next retry publishes and commits; startup recovery is not needed because the processor still holds its buffer.

D. A graceful shutdown

  1. serviceCalls Close on the streaming manager and the sqlmq dispatcher. The manager cancels its soft context.
  2. subscriberCloses the stream: awaitBroker("consumer cancel") around basic.cancel (noWait, a frame write). Deliveries stop; the worker drains its buffer according to its shutdown strategy, then exits. The subscriber waits up to shutdownTimeout, then forces the hard context.
  3. subscriberCloses the reader: awaitBroker("channel close") around channel.close.
  4. managerCloses the pool, which closes the shared connection: closer.Do, then the adapter's CloseDeadline(5 s). ConnectionClosed fires once.
  5. sqlmq processorStops its loops, closes the deferred handoff, and closes batch.Writer: bounded writer close, then connection close. The outbox channel stays open on purpose, because late handlers may still send on it.
  6. connectorClose on the connector closes anything still tracked. By this point the list is normally empty, because every connection released itself when it closed.

10The ten selects

Every select in the package, what it is waiting on, and which case is the one that makes it safe. If you are reading the code and lose the thread, find the row.

WhereCasesWhy it exists
connection.go watchClose<-done · reason, open := <-closesReport a close we did not ask for, exactly once. done ends the goroutine when we closed it ourselves; a nil reason or a closed channel is ignored for the same reason.
connection.go relayBlockedState<-done · n, open := <-notificationsDrain amqp091's capacity-one channel so its frame reader never blocks. Exits on done or when amqp091 closes the channel.
connection.go deliverLatest (first)<-done · defaultNon-blocking check so nothing is delivered after the connection closed, even if relay has room.
connection.go deliverLatest (loop)<-done · relay <- n · <-relayKeep only the latest blocked state. If the consumer has not taken the previous state, discard it and try again; never wait on a slow monitor.
connection.go Closed<-done · defaultA non-blocking liveness read for the streaming pool and the serialization decorator.
await.go awaitBroker (first)err := <-completed · <-timer.CThe bound itself. The call runs in its own goroutine because AMQP offers no per-call cancellation.
await.go awaitBroker (second)<-completed · <-timer.CAfter the sever, wait for the parked call to actually return. The timer is the guard against an adapter that leaves it pending.
stream.go Readsource, open := <-deliveries · <-ctx.Done()The consumer's blocking read. The context is the worker's read context, a child of the hard shutdown context.
stream.go endReason<-closes · <-cancels · <-timer.C (50 ms)Name the reason a stream ended. amqp091 can close deliveries a moment before the reason lands, so wait briefly, then settle for EOF.
stream.go Acknowledge<-ctx.Done() · defaultSkip the ack entirely if the caller's context is already gone; do not touch the broker for a batch nobody is waiting on.

Ten selects in eight functions: deliverLatest and awaitBroker each contain two. Nothing in connector.go, reader.go, writer.go, tls_dialer.go, or the adapter selects; they use context deadlines and awaitBroker instead.
